01 · Overview

What the migration is for

The M5 migration in the PowerODBA collection (ibm.power_aix_oracle_dba) is one playbook, m5_migration.yml, and three roles that automate a complete Oracle 19c database migration from x86 Linux to IBM AIX Power — end to end, as repeatable playbook runs instead of a manual, multi-day DBA runbook. It exists because that particular move crosses an endian boundary (x86 is Little-Endian, AIX Power is Big-Endian), which rules out the two normally-simplest migration paths — physical standby isn't supported across different endian platforms at all, and a plain export/import would work but is too slow for a real database. Oracle's supported answer to that specific problem is a documented procedure called M5 (MOS Doc 2999157.1); this playbook is that procedure, automated.

Concretely, it:

  • Validates both hosts and both databases against every M5 prerequisite before touching anything, and fails loudly with a specific remediation step rather than guessing
  • Deploys and drives Oracle's own DBMIG 5.1 driver tool for the repeatable RMAN backup/restore cycles that pre-stage the data
  • Runs the Data Pump Full Transportable cutover and verifies source-vs-destination table counts before it will let downtime end
  • Supports three topologies out of the box — Non-CDB → Non-CDB, Non-CDB → PDB, and PDB → PDB — selected by four variables, with no separate code path to maintain per topology
  • Is idempotent throughout: prechecks and the L0 baseline are safe to re-run, L1 is designed to run daily, and the irreversible go-live step is a deliberate, separate, opt-in command

Why incremental backups first

L0 (full baseline) and repeatable L1 (incremental) backups move nearly all of the data before the maintenance window opens. Only the L1F pass — the last, smallest incremental — happens during actual downtime.

Why Full Transportable

Data Pump Full Transportable Export/Import moves the schema/metadata across endianness in one pass, while the actual datafiles arrive via the RMAN restores that already ran — avoiding a slow row-by-row export of the whole database during downtime.

What DBMIG 5.1 does

Oracle's own driver script (dbmig_driver_m5.sh) generates the RMAN backup/restore commands and manages the transport-tablespace READ ONLY/READ WRITE flip. This collection deploys it, configures it, and drives it — it does not replace it.

Three supported topologies Non-CDB → Non-CDB, Non-CDB → PDB (source is a standalone database, destination is a pluggable database inside a container database), and PDB → PDB (both ends are pluggable databases) — selected entirely by four variables (mig_pdb, pdb_name, dest_cdb_sid, dest_pdb_name). See Topology flows below for the exact mechanics of each.

Detailed walkthrough

The same seven-phase shape as any RMAN cross-platform incremental migration — but the specifics below are this collection's actual behavior, not the general method. A few things a generic XTTS writeup gets right in principle work differently here, called out inline.

1

Pre-migration checks

  • Source version, edition, and endian format confirmed (Oracle ≥19.18.0.0.0, Enterprise Edition, Little-Endian source / Big-Endian destination)
  • The tablespace list to transport is identified — everything except SYSTEM, SYSAUX, UNDO, and TEMP, which are never transportable
  • DBMS_TTS.TRANSPORT_SET_CHECK runs against that list and must report zero violations — this is a hard gate before the baseline backup is even allowed to start, not something deferred to be patched up during import
  • Character set, NCHAR character set, and timezone file version are asserted to match source and destination exactly — no automated fix exists for a mismatch here
  • Source and destination do not need identical patch levels — only the same minimum version plus specific mandatory patches (the DataPump Bundle Patch on both sides, the RMAN cross-platform restore bugfix on the destination)
2

Database preparation

  • Tablespaces stay READ WRITE through this entire phase — the source keeps running normally; READ ONLY is only needed for the last few minutes at final cutover
  • Oracle's own DBMIG 5.1 driver and an identical working-directory tree are deployed to both hosts
  • How backup pieces move from source to destination is set once, up front: either SCP, or an existing shared filesystem mount (shared_filesystem: YES) — this collection doesn't support DBMS_FILE_TRANSFER or rsync as alternatives
3

Baseline backup and restore (L0)

  • Full RMAN backup of the transportable tablespaces on source, while still READ WRITE
  • Backup pieces transferred to the destination
  • Restored there — cross-platform datafile conversion happens automatically as part of the restore command itself (RESTORE ... FOREIGN DATAFILES ... FROM BACKUPSET), confirmed directly from a real generated cmdfile; there's no separate manual CONVERT DATAFILE step in this flow
  • This restored copy becomes the baseline everything else builds on
4

Incremental sync (L1, repeated)

  • Source keeps running and drifting ahead of the baseline
  • One or more incremental backups capture only what changed since L0 (or the last L1)
  • Each is restored, rolling the destination copy incrementally forward — run this daily, or on whatever cadence matches the real change rate, right up until the planned cutover
  • Each cycle shrinks how much data the final cutover pass has to move
5
⚠ Critical — downtime window

Final backup and restore (L1F) — the actual cutover step

  • Transportable tablespaces set READ ONLY on source — downtime starts here
  • The last incremental backup is taken and restored — the destination copy is now fully caught up
  • Because nearly everything already moved in phases 3–4, this pass is small and fast
6
⚠ Critical — the real pass/fail gate

Metadata import

  • Data Pump Full Transportable Import (impdp with TRANSPORT_DATAFILES) moves only the schema and metadata — the actual data is already on disk from the restores above
  • This plugs the transported tablespaces into the destination database's data dictionary
  • The real pass/fail gate here is a source-vs-destination row-count comparison — not a checksum comparison, and not DBMS_TTS.TRANSPORT_SET_CHECK again (that already ran, and only matters, before phase 3)
7

Post-migration and go-live

  • Transported tablespaces set back to READ WRITE on the destination — downtime ends here
  • Invalid objects recompiled, optimizer statistics refreshed
  • Once verified and accepted as production, the guaranteed flashback restore point Data Pump created is dropped — a separate, explicit, opt-in step, since it's irreversible
Outside this collection's scope Updating application connection strings/TNS entries, DNS or listener cutover, checksum-based data validation, and post-go-live monitoring are all real parts of a production migration — none of them are automated here. This collection stops at a verified, READ WRITE destination database with matching row counts; the application-facing cutover and ongoing monitoring are on you.
02 · Before you start

Prerequisites

Three environments are involved, each with its own requirements. Nothing here is automated by the collection except where noted — these are conditions the collection checks (and fails loudly on) rather than fixes for you.

controller  Ansible controller

Software

  • Ansible >= 2.14, Python >= 3.9
  • ansible.posix collection >= 1.4.0 (SSH key push)
  • SSH client access to both the source and destination hosts
  • ansible-vault password file (~/.vault_pass) — PowerODBA's ansible.cfg doesn't set one, so every command passes it

Files you stage yourself

  • Oracle's DBMIG_5.1.zip is Oracle-proprietary and not distributed with PowerODBA. Download it from My Oracle Support (Doc 2999157.1) and place it at roles/mig_prechecks/files/ — deploy_dbmig.yml copies it from there to both hosts. The repository's .gitignore keeps it out of git.
  • Real passwords still need to be filled into playbooks/vars/m5_migration/mig_vault.yml before encrypting it — see Download & install.
The DataPump Bundle Patch is not staged or installed by this collection Patch 38170982 is not a file anyone downloads or stages here, and this collection never runs opatch apply for it. It must already be applied — manually, by hand, on both the source and destination — before prechecks run. patch_apply_source.yml / patch_apply_dest.yml only run opatch lsinventory and assert the patch ID is found; if it isn't, prechecks fails with the exact ID to apply and stops there.

source  Source database host (x86 Linux)

  • Oracle 19c Enterprise Edition + Grid Infrastructure already installed and running, version >= 19.18.0.0.0
  • Platform confirmed Little Endian
  • Database in ARCHIVELOG mode
  • RMAN ENCRYPTION FOR DATABASE must be OFF (not supported by this procedure)
  • oracle OS user with SSH equivalence to the destination host (bidirectional)
  • DataPump Bundle Patch 38170982 already applied (checked via opatch lsinventory — the collection does not download or install it)
  • Sufficient free space under the working directory for RMAN backup pieces and the export dump file
  • If TDE is in use: keystore keys exported and imported into the destination manually beforehand, and a completion marker touched on the source host at done_dir/tde_keys_transferred.done (the collection only verifies this happened — it does not perform the key transfer)

destination  Destination database host (IBM AIX Power)

  • Oracle 19c Enterprise Edition + Grid Infrastructure already installed and running, version >= 19.18.0.0.0, confirmed Big Endian
  • Destination database already created and OPEN (non-CDB or CDB, per your topology) — this collection does not create the database itself
  • Database in ARCHIVELOG mode
  • compatible >= the source database's compatible value
  • NLS_CHARACTERSET, NLS_NCHAR_CHARACTERSET, and the V$TIMEZONE_FILE version must exactly match the source — there is no automated fix for a mismatch here; it requires a database rebuild
  • db_create_file_dest set to exactly one location (an ASM diskgroup or a filesystem path)
  • /bin/bash present — the vendor's impdp.sh uses bash-only array syntax; AIX's default /bin/sh is a real POSIX/Korn shell and will not run it correctly
  • DataPump Bundle Patch 38170982 already applied (checked, not installed, by the collection)
  • Bugfix 35564253 (RMAN cross-platform restore fix) applied as a standalone patch — unless the installed Release Update is >= 19.27.0.0.0, which already bundles it
  • If the source uses TDE: bugfix 30817822 applied (or RU >= 19.20 which bundles it)
  • If migrating from a physical standby: bugfix 35675516 applied
  • oracle OS user with SSH equivalence to the source host (bidirectional)
03 · Setup

Download and install

The migration ships inside the PowerODBA collection, ibm.power_aix_oracle_dba on Ansible Galaxy — install it like any other collection, then supply the one piece Oracle doesn't let anyone redistribute.

1

Install from Galaxy

Install the PowerODBA collection the normal way:

ansible-galaxy collection install ibm.power_aix_oracle_dba

Or work from a clone of github.com/IBM/ansible-power-aix-oracle-dba. Either way, the migration lives in playbooks/m5_migration.yml and roles/mig_*.

2

Install collection dependencies

From the collection's playbooks/ directory:

ansible-galaxy collection install -r ../collections/requirements.yml

Installs ansible.posix, which the migration needs for SSH key setup. All DBA/RMAN/Data Pump work runs via plain ansible.builtin.shell against sqlplus/rman/impdp.sh — no custom Python modules to build or ship.

3

Stage DBMIG

Download DBMIG_5.1.zip from My Oracle Support (Doc 2999157.1) and place it at roles/mig_prechecks/files/DBMIG_5.1.zip. deploy_dbmig.yml copies it from there to both hosts and unzips it. It isn't distributed with PowerODBA, and .gitignore keeps it out of the repository.

Not staged here: the DataPump Bundle Patch Patch 38170982 is a different thing entirely — it's not a file in files/ and this collection never applies it. It must already be applied by hand on both hosts before prechecks run; see Prerequisites.
4

Set up the vault

The migration has its own vault file, separate from PowerODBA's vars/vault.yml. From playbooks/, fill in the real passwords (SYS, SYSTEM) and encrypt it:

# edit vars/m5_migration/mig_vault.yml — set vault_sys_password and
# vault_system_password to real values

ansible-vault encrypt vars/m5_migration/mig_vault.yml

Then create the password file the runbook commands expect:

echo '<vault-password>' > ~/.vault_pass
chmod 600 ~/.vault_pass
5

Describe your environment

playbooks/inventory.yml is shared with the other PowerODBA playbooks, so the migration hosts sit in their own groups. Replace only the two host lines (<server hostname> ansible_host=<IP or DNS name>), keeping exactly one host in each group:

[mig_source]
source-linux-host ansible_host=333.33.33.333

[mig_destination]
dest-aix-host ansible_host=444.44.44.444

[mig:children]
mig_source
mig_destination

[mig:vars]
ansible_user=oracle
ansible_python_interpreter=/usr/bin/python3

[mig:children] lists group names, not hosts — leave it as is. [mig:vars] applies only to the two migration hosts: ansible_user is the account Ansible logs in as on those hosts. Host addresses come only from the inventory; the vars file derives them from each host's ansible_host.

playbooks/vars/m5_migration/mig_vars.yml — every migration parameter: SIDs, working directories, topology, tablespace list, credentials references, timeouts. See Variables file for the full list.

04 · Running it

How it's executed

Everything runs through one playbook, playbooks/m5_migration.yml, filtered by Ansible tags — one tag per stage. It calls each role directly; there's no import_playbook layer. Each stage is meant to be run as its own nohup'd background command from the playbooks/ directory, like the other PowerODBA playbooks, logging to its own file, so a multi-hour RMAN backup or Data Pump import survives an SSH disconnect. Every command passes -i inventory.yml (PowerODBA's ansible.cfg doesn't name an inventory) and --vault-password-file ~/.vault_pass (it doesn't set a vault password file; --ask-vault-pass can't prompt under nohup).

Inventory check The playbook's first play runs on the controller and checks that the inventory has exactly one host in [mig_source] and one in [mig_destination]. If -i inventory.yml was left out or the groups are missing, it stops straight away with "The inventory doesn't define the migration hosts. Run from the playbooks/ directory with -i inventory.yml…".

Prechecks

OS/DB validation, patch verification, SSH equivalence setup, source and destination DB preparation, DBMIG 5.1 deployment. Everything in this stage is a check-then-fix-manually or a one-time setup step — see mig_prechecks. It runs as one play across mig_source:mig_destination — every included task file carries its own host-group when:, so each host runs only its half — followed by a small play that marks the stage done. The idempotency gate is evaluated per host, against the same done-file on the source.

L1 — incremental backup + restore

Backs up only the blocks changed since the last L0/L1, restores them. No downtime. Run daily (or on whatever cadence fits the change rate) right up until the cutover window — each run shrinks the amount of data the final L1F pass has to move.

controller, from playbooks/nohup ansible-playbook m5_migration.yml -i inventory.yml --tags rman_l1 \
      --vault-password-file ~/.vault_pass > /tmp/m5_02_rman_l1_$(date +%Y%m%d).out 2>&1 &

Identical task sequence to L0 above (steps 2–8 in that list — the same mig_rman_L0_L1 role, just invoked with rman_level: L1), with two differences: no idempotency gate at the start (L1 is meant to run repeatedly), and no done-file written at the end. Each run's restore cmdfile and logs get their own timestamp, so multiple L1 runs leave multiple restore_L1_*.log files behind — run_impdp.yml later reads all of them, not just the latest.

L1F — cutover

The final incremental backup (this is what sets the transportable tablespaces READ ONLY on source — downtime starts here), restore on destination, Data Pump Full Transportable import, table-count verification against source, tablespaces flipped back to READ WRITE on destination (downtime ends here), recompile, stats, validation report. Unlike prechecks and L0/L1, this runs as separate plays — source, then destination, then a small completion-marker play — and the destination play itself is internally divided into 4 numbered stages, each with its own start/complete banner in the log.

Go live

Once the migration is verified and accepted as the new production database, this separate, explicit run finds the guaranteed flashback restore point impdp.sh created during import, shows you its name/SCN/creation time, pauses for a typed confirmation, then drops it. This step is never bundled into the cutover run above — see Operational notes for why that matters.

controller, from playbooks/ansible-playbook m5_migration.yml -i inventory.yml --tags golive_drop_restore_point --ask-vault-pass
  1. 1destinationQuery V$RESTORE_POINT for every before_imp_% restore point with guarantee_flashback_database = 'YES', ordered newest first
  2. 2destinationAssert exactly one was found — if zero or more than one, the run stops here and lists every one it found by name, SCN, and creation time rather than guessing
  3. 3destinationInteractive pause — explicit warning that this permanently removes the flashback safety net, requires pressing Enter
  4. 4destinationDROP RESTORE POINT <name>;
  5. 5destinationRe-query and assert it's actually gone
Idempotency Prechecks and L0 each write a done-file under done_dir — {{ m5_workdir }}/done on the source host, not the controller — once they succeed; re-running the same tag afterwards prints an "already completed" message and does nothing. Delete the relevant done-file on the source to force a re-run. L1 has no done-file gate — it's designed to run repeatedly. L1F writes rman_l1f.done when it finishes, but nothing checks for it before a run.
One shot, all stages ansible-playbook m5_migration.yml -i inventory.yml with no --tags at all runs every stage in sequence in a single invocation — useful for a fully unattended test run, less useful for production where L1 needs to repeat over days and L1F needs a deliberately chosen maintenance window.
05 · Architecture

Collection architecture

One playbook, three roles, one variables file, inside the PowerODBA collection. m5_migration.yml calls each role directly. Each role is tag-selected and host-scoped: prechecks and L0/L1 each run as a single play across mig_source:mig_destination, while L1F runs as one play per host group. Either way, tasks are guarded internally by when: inventory_hostname in groups[...].

09 · Operational notes

Things worth knowing before you run this for real

Drawn directly from real test runs against all three topologies — not hypothetical edge cases.

Restore points accumulate across retries

Every successful impdp.sh run mode creates a new guaranteed flashback restore point named before_imp_<timestamp>. If a cutover attempt fails partway and you re-run L1F, each attempt leaves its own restore point behind. The go-live drop step deliberately refuses to guess which one to drop once there's more than one — it lists all of them (name, SCN, creation time) and asks you to clean up manually via SQL*Plus first.

TNS alias name collisions

The collection writes a managed M5IMPDP alias into tnsnames.ora to work around a Data Pump connect-string parsing limitation. If a different, unmanaged entry with the same alias name already exists elsewhere in that file (e.g. left over from earlier manual testing), Oracle's resolver can pick the wrong one — with no error, just a silent wrong-database connection. Check for duplicate alias names if imports seem to be hitting stale data.

AIX's default shell is not bash

impdp.sh uses bash-only array syntax. AIX's /bin/sh is a genuine POSIX/Korn shell — running the script under it fails past the argument-parsing stage with no fatal error, silently imports nothing, and still reports success (rc=0). The collection always invokes it via bash impdp.sh explicitly.

Full Transportable Import logs benign noise

Errors like ORA-39083 against the internal GSMROOTUSER account, or "object already exists" for tablespaces/directories, show up on essentially every run and are not failures. verify_import.yml only ever surfaces these for context — verify_migration_correctness.yml's source-vs-destination table count comparison is the actual pass/fail signal.

An L1 with zero source-side changes is a hard stop, not a silent no-op

If nothing changed on source between the last backup and this L1 run, RMAN produces a genuinely empty incremental. Since there's nothing to copy or restore, the piece-sync step correctly finds zero pieces and fails loudly rather than pretending to succeed. This is expected on a quiet test database — make a real data change between L0/L1 runs to exercise the incremental path meaningfully.

Character set, NCHAR, and timezone mismatches have no automated fix

Unlike almost every other precheck, a mismatch here (os_checks_dest.yml) means a database rebuild on whichever side is wrong — there's no ALTER SYSTEM or patch that resolves it. Confirm these three match before investing time in the rest of the runbook.

A genuine non-CDB destination is uncommon

Most Oracle 19c installs default to the multitenant (CDB) architecture. If you point the automation at a CDB's root container while leaving the topology variables blank (Non-CDB → Non-CDB), Data Pump will reject creating ordinary local users at the root (ORA-65096, ORA-65046) — that combination only works when the destination instance was genuinely created without pluggable databases at all.

shared_filesystem controls a lot more than it looks

Beyond skipping the SCP steps, shared_filesystem: YES also blanks DBMIG's own DEST_SERVER property (so DBMIG doesn't redundantly SSH-copy files that are already visible on shared storage) — get this one setting right for the environment before the first L0 run, since it changes several tasks' behavior at once.

Clock skew across hosts can mislead file-based debugging

If the source, destination, and controller aren't NTP-synced, comparing file modification times across hosts to reconstruct "what ran when" can point at the wrong sequence of events. Database timestamps (SCN, restore point creation time) are the reliable source of truth when diagnosing a run after the fact.

A failed restore's log can outlive the failure — and this collection doesn't currently guard against that

run_impdp.yml deliberately unions every restore_L0_*.log / restore_L1_*.log / restore_L1F_*.log file it finds on disk (not just the latest per level), because L1 is meant to run repeatedly. That design doesn't currently distinguish a failed attempt's log from a successful one — a restore that fails partway still leaves its log sitting on disk under its normal name, so a later, separate L1F run can pick it up alongside the successful retry's log. If that failed attempt recorded a datafile path that's no longer valid on the retry (for example, if the datafile copy it referenced was deleted and re-created at a new path during cleanup), both paths get fed to impdp.sh's TRANSPORT_DATAFILES list — one of them stale. This is a real, currently-unaddressed gap, not a hypothetical: if an L0, L1, or L1F restore fails and you retry it, check {{ m5_workdir }}/log/ on the destination for that failed attempt's log file before running L1F's import, and move or rename it out of the way if there's any doubt about whether its recorded paths are still valid.

Run from playbooks/, with -i inventory.yml and the vault password

PowerODBA's ansible.cfg is shared and is found from the playbooks/ directory. It names no inventory and no vault password file, so every migration command passes -i inventory.yml and --vault-password-file. Leave out the inventory and the playbook's first play stops with a clear message; leave out the vault password and even --syntax-check fails with "Attempting to decrypt but no vault secrets found".

A full FRA quota stalls the database mid-run

When +FRA reached 100% of db_recovery_file_dest_size, archiving stopped and sessions hung on "log file switch (archiving needed)" — visible first as prechecks freezing on "Set USERS_DEF as database default tablespace". The diskgroup had plenty of free space; the quota was the limit. Check v$recovery_file_dest on both databases before L0 and size the quota for the archive logs a long baseline generates.

Done-files live on the source, and they're the only re-run switch

done_dir is {{ m5_workdir }}/done on the source host. If prechecks.done goes missing, the next --tags prechecks run re-runs every precheck for real — including the destination USERS → USERS_DEF replacement — instead of printing "already completed". Clearing m5_workdir during a reset also clears these markers, and the TDE key-transfer marker with them.

PDB→PDB restore errors are hidden from Ansible's output

run_restore.yml sets no_log when mig_pdb is 1, because the RMAN connect string carries the SYS password. A failed restore therefore shows only as "censored". The real error is in the restore log under {{ m5_workdir }}/log on the destination — that's where errors like ORA-17502: ksfdcre:4 Failed to create file appeared during testing.

The shared ansible.cfg applies to the migration too

The migration sets its own login user and Python interpreter in [mig:vars] and changes nothing in ansible.cfg. Keep remote_tmp = ~/.ansible/tmp there: a shared path such as /tmp/.ansible fails as soon as another user owns it on a host (see Troubleshooting). Output format, per-task timings and a separate Ansible log aren't set; add them for a single run with ANSIBLE_STDOUT_CALLBACK=yaml, ANSIBLE_CALLBACKS_ENABLED=timer,profile_tasks or ANSIBLE_LOG_PATH=….

10 · Troubleshooting

When something goes wrong

Real failures hit during testing of this collection, in Symptom → Cause → Fix form. A few are historical bugs already fixed in this collection — included anyway in case you're comparing against an older copy or hit something that looks similar.

Recovering from a failed run — full clean, then restart from Phase 1

This collection doesn't attempt any partial recovery, and doesn't clean up after itself. The recommended policy is deliberately simple rather than clever: if L0, L1, or L1F fails for any reason, don't try to resume mid-way — clean up everything below and restart the whole migration from prechecks. A targeted, partial cleanup can look correct and still leave something subtly stale (a leftover RMAN datafile copy, an old restore log with a now-invalid path); a full reset avoids that risk entirely.

prechecks — the one exception

Every task here is a pure check or an idempotent setup step (CREATE OR REPLACE, ALTER SYSTEM) — nothing destructive happens. Fix whatever the assert reported and re-run --tags prechecks directly, no cleanup needed.

Any L0, L1, or L1F failure — full reset

Regardless of which of the three failed, or at which internal step:

  1. 1destinationClear the RMAN repository — a failed or partial restore can leave incomplete datafile copies behind: 
    rman target /

CROSSCHECK DATAFILECOPY ALL;
LIST DATAFILECOPY ALL;
-- review the list, then:
DELETE DATAFILECOPY ALL;
  2. 2both hostsRemove everything under the M5 working directory ({{ m5_workdir }}, /u01/m5 by default) — every backup piece, cmdfile, and log from every attempt lives here, and none of it is safe to assume is still valid after a failure: 
    rm -rf {{ m5_workdir }}/*
    Prechecks re-stages everything this needs (DBMIG_5.1.zip, the directory tree, the properties file) on its next run, so there's nothing to preserve here. This also deletes done_dir, which lives under m5_workdir on the source — clearing the prechecks.done and rman_l0.done gates, which is exactly what a reset needs. It clears the TDE key-transfer marker too, so re-touch that before prechecks if TDE is in use.
  3. 3controllerClean up the controller side: 
    rm -f /tmp/m5_*.out
rm -f {{ precheck_report_dir }}/*
rm -f {{ validation_report_dir }}/*
    The done-files aren't here any more — step 2 already removed them with m5_workdir. This step is hygiene: clearing old logs and reports avoids confusing an old run's output with the new attempt.
  4. 4restartRe-run from the top: --tags prechecks, then rman_l0, then rman_l1 as needed, then rman_l1f.

go-live

Different case — this only reads V$RESTORE_POINT and pauses for a typed confirmation before doing anything destructive, so it's always safe to retry without any cleanup. See the "finishes but drops nothing" and "Found 2 ... expected exactly 1" entries below for the two ways it can stop short.

Specific failures seen in testing

Import reports success but nothing was actually imported

Symptom

impdp.sh exits with rc=0, but the destination ends up with 0 tables and no guaranteed restore point.

Cause

The script was invoked as sh impdp.sh. AIX's /bin/sh is a real POSIX/Korn shell and can't parse the script's bash-only array syntax — it fails partway through silently and never populates the file list, but still exits 0.

Fix

Always invoke it as bash impdp.sh ... — already this collection's default. If a custom change reintroduces sh, this is the first thing to check.

Import fails with ORA-65096 or ORA-65046

Symptom

ORA-65096: invalid common user or role name or ORA-65046: operation not allowed from outside a pluggable database during import.

Cause

The destination is actually a container database, but the topology variables were left blank as if it were Non-CDB → Non-CDB — Data Pump ended up connecting to the CDB root, which refuses to create ordinary local users.

Fix

Set dest_cdb_sid and dest_pdb_name to target the real pluggable database (Non-CDB → PDB or PDB → PDB topology) instead.

Import connects to the wrong database

Symptom

tnsping M5IMPDP resolves to a database you didn't expect, or the import silently touches old/unrelated data.

Cause

A second, unmanaged M5IMPDP entry already existed in tnsnames.ora — from earlier manual testing — outside the collection's own managed block. Oracle's resolver picked that stale entry instead.

Fix

Search tnsnames.ora for more than one M5IMPDP = entry and remove the one outside the ANSIBLE MANAGED BLOCK markers.

L1 fails with "No backup piece paths found"

Symptom

The L1 or L1F backup-piece sync step fails: "No backup piece paths found in ... cmdfile parsing may need review."

Cause

Usually not a parsing bug — nothing changed on the source between the last backup and this incremental, so RMAN genuinely produced a zero-byte backup with nothing to copy.

Fix

Make a real data change on source (insert/update, then commit) before re-running L1. Rarely an issue in production, where there's normally ongoing activity between runs.

Go-live command finishes but drops nothing (ok=1, no error)

Symptom

--tags golive_drop_restore_point completes cleanly with no failures, but the restore point is still there.

Cause

(historical) — Ansible doesn't propagate tags from a dynamic include_tasks statement into the included file's own tasks. The include fired correctly, but every task inside it was then filtered out as untagged.

Fix

Already fixed in this collection — the tasks are wrapped in a block explicitly tagged golive_drop_restore_point. If you're on an older copy without that fix, add the block tag.

Go-live command refuses to proceed: "Found 2 ... expected exactly 1"

Symptom

The go-live step stops with a message listing two or more restore points instead of dropping one.

Cause

Repeated or partially-failed L1F attempts each created their own guaranteed restore point, and none of the earlier ones were ever cleaned up.

Fix

The error message itself lists every restore point (name, SCN, creation time) — drop the ones you don't want via SQL*Plus as sys, then re-run once only one remains.

Guaranteed restore point exists but the collection reports "none captured"

Symptom

SELECT * FROM V$RESTORE_POINT clearly shows a BEFORE_IMP_... row, but verify_import.yml and the validation report say no restore point was found.

Cause

(historical) — the lookup query matched against a lowercase 'before_imp_%' pattern, but Oracle stores unquoted restore point names in uppercase, and LIKE is case-sensitive.

Fix

Already fixed — the query now uses UPPER(name) LIKE 'BEFORE_IMP_%'.

Prechecks fails on character set, NCHAR, or timezone mismatch

Symptom

Prechecks stops with a hard assert comparing source vs destination charset, NCHAR charset, or timezone file version.

Cause

Source and destination were created with genuinely different settings — this isn't something Full Transportable Import can reconcile in flight.

Fix

No ALTER SYSTEM fixes this. Timezone version can be upgraded via DBMS_DST on the lagging side; a character set mismatch requires a database rebuild. Confirm all three match before investing further time.

Setting tablespaces READ WRITE fails with ORA-01646

Symptom

The postcheck stage fails partway through with ORA-01646, and only some tablespaces end up READ WRITE.

Cause

(historical) — ALTER TABLESPACE ... READ WRITE isn't idempotent; the task used to issue it unconditionally, and it errors on a tablespace that's already READ WRITE (like a pre-existing USERS).

Fix

Already fixed — the task checks each tablespace's current status first and only alters the ones actually READ ONLY.

Import log shows GSMROOTUSER errors or "object already exists"

Symptom

ORA-39083 against GSMROOTUSER, or "already exists" messages for tablespaces/directories, appear in the import log.

Cause

Benign noise from Full Transportable Import — GSMROOTUSER is Oracle's own internal Global Data Services account, and "already exists" objects are expected on re-runs.

Fix

Nothing to do — these show up on essentially every run. Check verify_migration_correctness.yml's table-count result for the real pass/fail signal, not the raw log.

"The inventory doesn't define the migration hosts"

Symptom

The first play, "M5 migration — check inventory", fails and nothing else runs.

Cause

The playbook was run without -i inventory.yml, or [mig_source] / [mig_destination] are missing or don't hold exactly one host each.

Fix

cd to playbooks/, run ansible-playbook m5_migration.yml -i inventory.yml …, and keep exactly one host in each migration group.

"Attempting to decrypt but no vault secrets found"

Symptom

Any command — even --syntax-check — stops with this error.

Cause

mig_vault.yml is encrypted and PowerODBA's ansible.cfg doesn't name a vault password file.

Fix

Add --vault-password-file ~/.vault_pass, or --ask-vault-pass when running interactively.

"Failed to create temporary directory" — reported as UNREACHABLE

Symptom

A host fails on its first task with UNREACHABLE … Failed to create temporary directory, although SSH works.

Cause

remote_tmp points at a directory the oracle user can't write to — typically a shared path such as /tmp/.ansible that another user (for example root, mode drwx------) created first.

Fix

Keep remote_tmp = ~/.ansible/tmp in ansible.cfg, or give the migration hosts their own by adding ansible_remote_tmp=~/.ansible/tmp to [mig:vars] in inventory.yml.

Prechecks hangs on "Set USERS_DEF as database default tablespace"

Symptom

The task never returns; v$session shows sessions waiting on "log file switch (archiving needed)".

Cause

The FRA hit its db_recovery_file_dest_size quota (v$recovery_file_dest at 100% used, nothing reclaimable), so archiving stopped and anything needing a log switch waits.

Fix

Raise db_recovery_file_dest_size, or back up and delete archived logs to free FRA space. The stuck session continues on its own once archiving resumes.

RMAN restore fails and Ansible shows only "censored"

Symptom

ASYNC FAILED on the destination, followed by censored: the output has been hidden due to the fact that 'no_log: true' was specified.

Cause

Expected for PDB→PDB — the restore runs with no_log because its connect string carries the SYS password. The underlying error is in the restore log, not the Ansible output.

Fix

Read the newest restore_<level>_*.log in {{ m5_workdir }}/log on the destination. During testing it showed ORA-17502: ksfdcre:4 Failed to create file, on a different datafile each retry; the root cause wasn't confirmed. Check FRA and ASM space and the ASM alert log, then follow the full reset above before retrying.
